## 🤔有关学习、思考小Tips

1. 学会独立思考与解决问题，也要学会正确看待 AI

   AI 大模型已经能够帮助我们完成许多工作，但**能够借助 AI 完成任务，不代表自己真正掌握了完成任务所需要的能力**

   对于基础阶段的学习，我们更希望你能亲自经历搜索资料、阅读文档、编写代码、排查错误和整理思路的过程，以此来提升大家的逻辑思维能力

   因此，**除「AI 工作流」选做拓展外，其他考核任务原则上建议不要使用 AI 完成**

   尤其希望大家注意：

   - **代码自己动手写**：不要仅仅依靠 AI 生成代码来完成任务；
   - **笔记自己理解后整理**：不要直接把 AI 生成的内容当作自己的学习记录；
   - **问题自己尝试解决**：遇到报错、困难时，先尝试查阅资料、分析原因，也可以向 mentor 交流求助

  **这并不是否定 AI 的价值，而是希望大家先建立基本的独立学习、判断和实践能力**

   等到你真正理解了自己在做什么，再去探索如何利用 AI 提高效率、拓展能力，也许会有不同的收获

   **AI 可以帮助你走得更快，但你也需要拥有独立前行的能力**

2. 强烈建议使用 Google 搜索引擎搜索所需内容，可以尝试思考一下为什么我们推荐 **Google**🧐

   如果发现用不了 Google ，可以进一步思考原因以及解决方案

   同时，搜索到结果只是第一步

   - 试着区分官方文档、社区讨论、个人博客与 AI 生成内容；
   - 当不同来源给出不同答案时，想想应该相信谁，为什么可以相信，以及如何验证这些文献说的是不是真的？

3. **不要只满足于「我做出来了」，试着追问「为什么」**

   代码能跑起来固然很好，但它为什么能够运行？换一种情况还成立吗？如果出现错误，你能不能解释原因？

   学习时不妨多问几个为什么，也可以尝试改变一些条件，看看结果会发生什么变化

   不必每次都把所有底层原理研究透彻，但至少可以试着分清：

   - 我知道它怎么用了；
   - 我理解它为什么这样工作；
   - 我知道它在什么情况下可能不再适用。

   **知道怎么做是一回事，理解为什么这么做，又是另一回事**

4. **学会比较、权衡，而不只是寻找一个「最好的答案」**

   很多问题其实没有唯一的最优解，更多的可能是一种 trade-off

   一种方法可能更简单，但性能有限；另一种可能更高效，却需要付出更多学习和维护成本

   当你学习一种技术或者选择一种方案时，不妨想想：

   - 它究竟解决了什么问题？
   - 为什么要这样做，有没有其他方法？
   - 它适合什么场景，又有什么局限？
   - 我们为此付出了什么代价？

   不要只看一个方案的优点，也试着找找它的缺点和反例

   **技术是解决问题的手段，而不是目的本身**

5. **保持独立思考，也要敢于质疑**

   无论是教程、博客、AI 给出的回答，还是 mentor 提供的建议，都不一定是唯一正确的答案

   有疑问时，可以查证、尝试，也可以提出不同意见
   但质疑不只是说「我觉得不对」，更重要的是尝试说明为什么，并找到支持自己判断的依据

   当然，也要允许自己犯错，允许自己的想法被推翻

   不必为了质疑而质疑，也不必为了认同而认同

   **重要的不是永远正确，而是逐渐拥有独立判断和修正判断的能力**

6. **希望你不只是从 Geek 获得些什么，也能在这里留下一点什么**🫡

   可以是一份有帮助的笔记、一次问题讨论、一个小项目，也可以是给后来者留下的一条经验

   这些东西或许很小，但当它们慢慢积累起来，就可能帮助更多后来的人

   我们不要求每个人都做出多么厉害的成果，也不希望分享和贡献成为一种额外负担

   只是希望，在这里学到东西的同时，你也能慢慢找到自己愿意探索、愿意分享的事情

   **让自己的探索成为别人的启发，也让别人的经验成为自己继续前进的起点**
   > 这里在校的 Geek 全体成员向历代 Geek 组建设发展过程中的前辈们致敬🫡

8. **好奇之心，改变之力**

   或许你现在还不知道自己向往什么、感兴趣什么，但当你具备了好奇之心，那么它本身就是你前进的动力，往前走吧
   
   有时候，一个偶然遇到的问题、一个想尝试的小想法，就可能成为一段新旅程的起点，加强我们的技术能力，相信总有一天，我们能够为开源社区，技术世界贡献出我们的 “改变之力”！
   
   **Keep Curiosity.**

## ❗❗❗有关考核注意事项

1. 创建 `GitHub` 任务仓库，阶段一大家可以直接在 GitHub 的 Web 端进行上传，
   但在阶段二以后，**须通过 Git 命令行把个人学习记录远程推送到自己的仓库中**

2. 每位同学的阶段任务**由各自 mentor 检查**，

   在阶段一完成后，需将自己的 **GitHub 仓库链接私发给对应 mentor**，
   别让 mentor 久等哦~

   > 每阶段完成后，请大家**主动**向 mentor 说明完成情况
   >
   > 比起在阶段时长内未完成任务内容，更让我们难以接受的是：
   > 没有按时完成，也没有提前与 mentor 说明情况

3. 无论何时，都要**注意大小写**。也许现阶段你感觉大小写并不影响理解，但未来你会发现，

   规范的大小写会帮你省很多事儿。(例如 如果能注意 Geek 而非 geek 的话，会让你看起来更严谨~)

4. 不同的仓库 README 风格不一样，有关我们的考核仓库的 **README** ，
   我们倾向于大家做成一个**索引清晰、分层合理、链接可点**的 README ，
   方便我们定位大家的笔记、部署网页的位置

5. **学习态度**也是考核期的一个重要内容，有问题可以及时和 mentor 沟通，坚持到最后一定会有所收获

6. **请留意特殊说明的 [选做-进阶] 任务，这对考核或许只是一个小加分，但对你自己来说或许是一个大成长**

7. **[加分项]** 随手记录你遇到的问题和解决过程，上传到 Github ，问题大小不限，记录本身就是好习惯哦~

   不必只记录成功的结果。一次失败的尝试、一个还没解决的问题，如果能说明尝试过程和自己的思考，同样有价值。

8. 每阶段都有阶段时间，也是我们的推荐完成时间，
   **但，那只是参考，不是闹钟，别等它响了才开始动**

   有能力的，早点跑；遇到困难的，也不必为了赶进度而忽略理解
   请留意各阶段的具体截止要求，如果无法按计划完成，记得提前和 mentor 沟通

9. 学习过程中总会收集到一些资料、资源，不妨将其也放在问题解决记录里面，

   这样大家再遇到相似的问题，就可以迅速找到资料，提高解决效率

   如果可以，顺手注明资料来源、适用范围，以及你觉得它有帮助的原因，会更方便后来的人理解和使用。

10. 有些阶段的内容会藏着一些有趣的点，希望大家可以在学习过程中找到呀~
    也欢迎你在考核任务之外，尝试一些自己感兴趣的东西

11. **这份考核书并不是标准答案，也不是学习的终点**

    我们提供的是一条帮助大家入门的路径，而不是要求所有人沿着同一条路走下去

    如果你发现了更好的学习资料、更合适的实现方式，甚至觉得某些考核任务存在问题，都欢迎提出自己的想法

    不必因为某个内容是学长学姐写的，就认为它不能被修改

    只要有充分的理由，欢迎大家通过 Issue、PR 或直接交流的方式，一起让它变得更好

    **我们希望传递经验，但也欢迎后来者重新思考这些经验。**

## 写在最后

或许刚刚进入大学的你，还不太清楚自己对什么感兴趣，未来想走向哪里，也不知道现在学的这些东西究竟能带来什么

没关系，不必急着找到答案

希望你能在这里接触到一些以前不了解的东西，遇到一些愿意一起讨论问题的人，也逐渐发现一些真正让自己感兴趣、愿意花时间弄明白的问题

我们希望你不仅能够学会使用工具、完成项目、解决问题，也能逐渐学会发现问题、提出问题，尝试创造属于自己的答案

你可以从前人的经验中获得帮助，也可以质疑它、改变它，甚至走向我们尚未探索过的方向

不必急着证明自己有多厉害，也不必因为暂时找不到方向而感到焦虑

**保留好奇，保持思考，勇于尝试**

或许有一天，你会发现，曾经让自己困惑的问题，已经成为了你继续探索的起点；而你留下的某一点经验，也正帮助着后来的人

**考核有阶段，学习和探索却不必止步于考核**

*Keep Curiosity. The Power Of Change.*
